# Evaluating measures, SQL functions, and filter semantics

When translating SQL `SELECT` projections and `WHERE` clauses into LookML measures, agents must separate presentation formatting and query-time slicing from semantic aggregation. Naive 1:1 SQL translation introduces silent metric bugs (unfiltered measures with filtered names, row-level rounding drift, broken symmetric aggregates, and duplicate hidden helper measures).

Apply this guide to **every** query—including `simple_single_table` queries without `CASE WHEN`.

## SQL function and wrapper evaluation matrix

| SQL projection pattern | What it means in SQL | LookML resolution | Anti-pattern to avoid |
| :--- | :--- | :--- | :--- |
| `ROUND(<agg>, k)`, `TRUNC(<agg>, k)`, `CAST(<agg> AS NUMERIC)` | Presentation formatting (99% of queries) | Strip the outer wrapper. Model **one** native aggregate measure (`type: sum`, `type: average`, `type: number`) and set `value_format_name` from Looker's built-in names (`decimal_0`..`decimal_4`, `usd`, `usd_0`, `eur`, `eur_0`, `gbp`, `gbp_0`, `percent_0`..`percent_4`, `id`) or a custom `value_format` (`lkr parse lookml-to-api --validate` rejects unknown `value_format_name`s). | Putting `ROUND(${col}, 2)` inside `type: sum` (compiles to row-level `SUM(ROUND(col, 2))` and drifts across large tables), or splitting into a hidden `type: sum` + visible `type: number` `ROUND(${base}, 2)` pair ($2\times$ measure bloat and precision loss in downstream ratios). |
| `100.0 * <num_agg> / <den_agg>` or `<agg>(<ratio>) * 100` (with or without `ROUND`) | Percentage display scaling | Strip `100.0 *` / `* 100` and `ROUND`, and rename `*_pct` / `*_percent` suffixes to `*_share` / `*_ratio` / `*_rate` so the identifier matches its unscaled `[0, 1]` value. For post-aggregation ratios (`100.0 * SUM(a) / NULLIF(SUM(b), 0)`), model an unscaled `type: number` ratio (`1.0 * ${num} / NULLIF(${den}, 0)`, `tags: ["non_additive"]`) with `value_format_name: percent_2` (or `percent_1`, `percent_0`), asserting `round(${view.measure}, 4)` in `.test.lkml`. For per-row ratio averages (`AVG((retail_price - cost) / NULLIF(cost, 0)) * 100`), model an unscaled ratio dimension (`markup_ratio`: `(${retail_price} - ${cost}) / NULLIF(${cost}, 0)`) and `type: average` measure (`avg_markup_ratio`: `sql: ${markup_ratio} ;;`, `tags: ["non_additive"]`) with `value_format_name: percent_2` (`pre_gate.py` automatically aligns unscaled `percent_*` Looker values against `* 100` SQL projections). | Baking `* 100` into LookML `sql:` alongside `percent_*` (renders `4,250%` instead of `42.5%`), keeping a `*_pct` name on an unscaled `[0, 1]` ratio, or pairing `* 100` with a literal `"0.00\"%\""` `value_format` (`lkr parse lookml-to-api --validate` rejects this because it inflates Excel/CSV exports, Table Calculations, and downstream math by $100\times$ and shifts `FLOAT64` order of operations from `AVG(x) * 100` to `AVG(x * 100)`). |
| `COALESCE(<agg>, 0)`, `IFNULL(<agg>, 0)` | Display-layer null zeroing | Strip the wrapper. Use a native aggregate (`type: sum`, `type: count`, `type: average`). | Wrapping `COALESCE(SUM(${col}), 0)` in `type: number`, which bypasses Looker's symmetric aggregates on `one_to_many` joins. |
| `COUNT(*)` or `COUNT(pk)` / `COUNT(DISTINCT pk)` (non-null PK) | Row count at table grain | Reuse the autogenerated `measure: count { type: count }`; refine its `description:` and optional standalone-honest `synonyms:` in `bronze/:table.refinement.lkml` (only set `label:` when creating a brand-new Explore—existing Explores already snapshot `count`'s default `"Count"` label in `measures.snap.json.md` even if `.refinement.lkml` omits `label:`, so never read `measures.snap.json.md` to check; `lkr parse sql-lookml-compare` maps `COUNT(*)`, `COUNT(pk)`, and `COUNT(DISTINCT pk)` directly to `<view>.count`). | Creating a duplicate `type: count` measure on the same view (`lkr parse lookml-to-api --validate` rejects duplicate logic), mutating an already-snapshotted `label:` on `count`, or adding a `WHERE`-filtered SQL alias as a `synonyms:` entry on unfiltered `count`. |
| `COUNT(nullable_col)` (non-PK column) | Count of rows where `nullable_col IS NOT NULL` | If `nullable_col` is a date/timestamp (`sold_at`), define a positive `type: yesno` dimension (`is_sold`: `${sold_raw} IS NOT NULL`) and filter on `filters: [is_sold: "yes"]`; otherwise `type: count` with `filters: [nullable_col: "-NULL"]` or a Custom Measure. | Mapping `COUNT(sold_at)` to unfiltered `measure: count`, which counts `NULL` rows that SQL ignored. |
| `COUNT(DISTINCT col)` (non-PK column) | Distinct entity count | Model `type: count_distinct` with `sql: ${col} ;;` (or `APPROX_COUNT_DISTINCT` per [13-large-tables-and-partitioning.md](13-large-tables-and-partitioning.md)) using a canonical plural/count identifier (`unique_sessions` or `session_count`, `distinct_users` or `user_count`—never ending in `_id`). | Using `type: number` with raw `COUNT(DISTINCT ...)`, copying quirky SQL aliases verbatim (`unique_chaotic_sessions`), or naming `count_distinct` measures with an `*_id` suffix (`unique_session_id`), which suppresses Looker's default comma formatting. |
| `PERCENTILE_CONT`, `PERCENTILE_DISC`, `APPROX_QUANTILES`, `MEDIAN` | Quantile or median aggregation | Model native `type: percentile` (`percentile: <N>`, `sql: ${col} ;;`) or `type: median` (`sql: ${col} ;;`). Looker's BigQuery, Snowflake, and Postgres dialect generators automatically promote `type: percentile` and `type: median` to `percentile_distinct` / `median_distinct` across fanout joins with zero Liquid. | Putting `PERCENTILE_CONT(...) OVER()` (breaks `GROUP BY` in BigQuery), `PERCENTILE_DISC`, `APPROX_QUANTILES`, or `MEDIAN` inside `type: number` (`lkr parse lookml-to-api --validate` rejects raw percentile SQL), or adding brittle `{% if child._in_query %}` Liquid guards. |
| `STDDEV`, `STDDEV_SAMP`, `STDDEV_POP`, `VARIANCE`, `VAR_SAMP`, `VAR_POP` | Sample ($N - 1$) or population ($N$) dispersion | Decompose into column-scoped **hidden symmetric-aggregate intermediate measures** (`hidden: yes` unless requested in `input.sql` / `metrics.md`, reusing any existing unfiltered `total_<col>` or non-null `count`) + algebraic `type: number` formula (see template below). | Raw `STDDEV*(${col})` or `VAR*(${col})` inside `type: number` (breaks across `one_to_many` joins and is rejected by `lkr parse lookml-to-api --validate`), or generic `true_count` / `true_sum` helper names that collide across columns or trip `duplicate_field_logic`. |
| `SUM(col_a - col_b)` or `SUM(col_a * col_b)` | Row-level linear arithmetic before aggregation | Single-table DAG: dimension + `type: sum` in `bronze/:table.refinement.lkml`. Multi-view DAG (`${order_items.sale_price} - ${inventory_items.cost}`): dimension + `type: sum` in `silver/:view_a_:view_b_fields.view.lkml` (bare-joined). | Putting multi-view `${other_view.col}` references inside a Bronze refinement. |
| `SUM(a) / NULLIF(SUM(b), 0)` | Post-aggregation ratio | Atomic `type: sum` measures + `type: number` (`sql: 1.0 * ${total_a} / NULLIF(${total_b}, 0) ;;`), or a Query-layer Table Calculation if ad-hoc ([02-conditional-measures-and-bucketing.md](02-conditional-measures-and-bucketing.md)). | `AVG(a / b)` (average of ratios $\neq$ ratio of sums) or raw `SUM(a) / SUM(b)` inside `type: number`. |
| `EXTRACT(YEAR \| MONTH \| DAYOFWEEK \| ISODOW \| HOUR \| QUARTER \| DAYOFYEAR FROM ts)` or `TIMESTAMP_DIFF(end_ts, start_ts, <UNIT>)` | UTC calendar/clock part or exact timestamp duration on raw `TIMESTAMP` / `DATETIME` | Reference `${<group>_raw}` (`type: number`, `sql: EXTRACT(YEAR FROM ${created_raw}) ;;` with `value_format_name: id`, or `EXTRACT(DAYOFWEEK \| HOUR FROM ${created_raw}) ;;`; allowed by `lookml-to-api --validate` alongside `dimension_group` timeframes when SQL evaluates in UTC or performs integer arithmetic like `oi_year - signup_year`, where `WHERE expr_a >= expr_b` maps to filtering `diff_dim: ">=0"`). For durations between two `TIMESTAMP` columns (`second`/`minute`/`hour`/`day`), native `dimension_group` `type: duration` with `${<start>_raw}` and `${<end>_raw}` compiles directly to BigQuery `TIMESTAMP_DIFF(sql_end, sql_start, <UNIT>)`. | Substituting `${<group>_day_of_week_index}` (`0..6` Monday-start) for BigQuery `DAYOFWEEK` (`1..7` Sunday-start), or using timezone-converted timeframes (`hour_of_day`, `day_of_week`, `date`, `year`) without `convert_tz: no` when raw SQL evaluates in UTC. |

> **When to keep SQL `ROUND` (the 1% exception):** Keep SQL rounding only when `metrics.md` or warehouse accounting rules explicitly require pre-rounded ledger math before downstream SQL subtraction/comparison, or when `ROUND(col, k)` is deliberately applied *per row* before summing (such as per-invoice tax rounding).

### Native percentiles (`type: percentile` / `type: median`) and symmetric `STDDEV` / `VARIANCE`

`lkr parse lookml-to-api --validate` rejects any `type: number` measure whose `sql:` AST calls `PERCENTILE_CONT`, `PERCENTILE_DISC`, `APPROX_QUANTILES`, `MEDIAN`, `STDDEV*`, or `VAR*`. Always model quantiles natively and decompose dispersion into symmetric intermediate measures scoped by `<col>`:

```lookml
measure: p99_revenue {
  type: percentile
  percentile: 99
  sql: ${revenue} ;;
  value_format_name: usd
}

# Symmetric STDDEV / VARIANCE helpers scoped to <col> (`hidden: yes` unless requested):
# Skip _<col>_count and use ${count} when <col> is NOT NULL; reuse existing unfiltered total_<col>
# instead of _<col>_sum (or promote _<col>_sum -> total_<col> with `alias: [_<col>_sum]` later).
measure: _revenue_count {
  hidden: yes
  type: count_distinct
  sql: ${order_id} ;;
  filters: [revenue: "-NULL"]
}
measure: _revenue_sum {
  hidden: yes
  type: sum
  sql: ${revenue} ;;
}
measure: _revenue_sum_of_squares {
  hidden: yes
  type: sum
  sql: POWER(${revenue}, 2) ;;
}

# Sample STDDEV (N - 1); use NULLIF(${_revenue_count}, 0) for POP and drop SQRT(...) for VARIANCE:
measure: stddev_revenue {
  type: number
  sql: SQRT(GREATEST(${_revenue_sum_of_squares} - (POWER(${_revenue_sum}, 2) / NULLIF(${_revenue_count}, 0)), 0) / NULLIF(${_revenue_count} - 1, 0)) ;;
  value_format_name: usd
}
```

## `WHERE` predicates vs. intrinsic metric `filters:` ("No Lying Measure Names or Synonyms")

**Hard invariant:** Every LookML measure's identifier, `label:`, `description:`, and `synonyms:` must accurately describe what that measure computes **standalone** (with zero Explore `WHERE` filters applied). Never name, label, or attach a `synonyms:` entry to an unfiltered measure after a `WHERE`-filtered SQL alias.

### Canonical LookML field naming, `count` / `count_distinct` comma formatting, `synonyms:`, and `alias:`
- **Sanitize colloquial SQL aliases into canonical domain identifiers (for newly authored fields):** When `sql-lookml-compare` maps a SQL expression to an **already-committed LookML field** (even with a legacy name like `events.unique_chaotic_sessions`), reuse that committed field as-is rather than renaming or duplicating it unless explicitly asked to rename. For **newly authored** fields, normalize quirky or one-off SQL `AS` aliases (`unique_chaotic_sessions`, `distinct_clicking_humans`, `markup_greed_pct`, `avg_markup_greed_pct`) into reusable domain names (`unique_sessions` or `session_count`, `distinct_users` or `user_count`, `markup_ratio`, `avg_markup_ratio`), while preserving business persona terminology and secondary SQL aliases from `metrics.md` / `input.sql` in `label:` (`"Catalog Markup Greed Ratio"`), `description:`, and `synonyms:` (`["catalog markup greed ratio", "markup pct"]`) (`pre_gate.py` pairs unmatched columns deterministically via `inline_query.fields` order).
- **Default comma formatting on `type: count` and `type: count_distinct`:** Looker applies identical default thousands-separator commas to `type: count` and `type: count_distinct` across Explore tables, tiles, and formatted CSV/TXT/HTML/Markdown exports whenever the field is not a primary key and its LookML name does **not** end in `id`, `year`, or `decade`. Naming a `count_distinct` measure after its key column (`count_distinct_user_id`, `unique_session_id`) suppresses default commas because of the `id` suffix—always use plural/count names (`unique_sessions`, `user_count`) instead. Skip blanket `value_format_name: decimal_0` on non-`*id` count measures unless explicit `.xlsx` `#,##0` styling (or Grid inline sparkline+total / reference-line formatting, or a legitimate `*(id|year|decade)` field name) is required, in which case `type: count` and `type: count_distinct` need `decimal_0` equally.
- **`synonyms: ["..."]` (API/NLQ vocabulary bridge, zero field bloat):** Use `synonyms:` (requires New LookML Runtime, Looker's default) when `metrics.md` or `input.sql` (`AS <alias>`) uses a genuine business term, acronym (`"GMV"`, `"AOV"`), or standalone-honest SQL column alias that differs from `label:`. Never generate thesaurus filler (`["total cost", "sum of cost"]` when `label: "Total Cost"` covers it), and never attach a `WHERE`-filtered alias (`"unsold units on shelf"`) to an unfiltered field (`inventory_items.count`).
- **`alias: [old_field_name]` (URL/API rename redirect only):** Use `alias:` **strictly** when renaming an already-committed LookML field so saved Looks, dashboards, `/x/` URLs, and SDK queries referencing `<view>.<old_field_name>` continue working (for `dimension_group`, place `alias: [old_group]` on the group itself). Never put `alias:` on newly authored fields, never copy a SQL `AS` alias into `alias:`, and never reference aliased names inside LookML (`${...}`, `filters:`, `query:`, `explore_source:`, or `test:`).

When an input query applies a `WHERE` predicate (or repeats the same `CASE WHEN` across projections), inspect both `input.sql` and `metrics.md` to pick one of two honest paths:

| Scenario | Signal in `input.sql` + `metrics.md` | Prescribed LookML action |
| :--- | :--- | :--- |
| **1. Intrinsic filtered domain KPI** | `metrics.md` defines a named, recurring business metric whose meaning inherently depends on the predicate (e.g., *"Unsold Dusty Shelf Inventory Cost: wholesale cash tied up in physical stock sitting unsold on warehouse shelves"* with `WHERE sold_at IS NULL`). | Bake `filters:` directly onto `sunk_dusty_shelf_cost` (`type: sum`, `sql: ${cost} ;;`, `value_format_name: usd`). When the predicate checks date/timestamp nullability (`sold_at IS NULL` / `IS NOT NULL`), promote **one** positive-polarity `type: yesno` dimension on the `raw` timeframe (`is_sold`: `${sold_raw} IS NOT NULL`, see [02-conditional-measures-and-bucketing.md](02-conditional-measures-and-bucketing.md)) and use `filters: [is_sold: "no"]`—never create negated or opposite twins (`is_unsold`, `is_not_sold`, or unrequested `sold_inventory_cost` / `total_cost` measures). |
| **2. Ad-hoc or report-level `WHERE` slice** | `WHERE` scopes a time window, region, or cohort for the query (`WHERE created_at >= '2026-01-01'`, `WHERE country = 'US'`), or filters general table metrics that are not intrinsically tied to that predicate. | Strip `WHERE` into the Explore Quick Start `query: { filters: [...] }` and `run_inline_query` `filters` (still promoting a `type: yesno` dimension if the slice is a date `NULL`/`-NULL` check; for date bounds on `<group>_date`, Looker's `"after YYYY/MM/DD"` is inclusive `>=`, `"before YYYY/MM/DD"` is exclusive `<`, `"YYYY/MM/DD to YYYY/MM/DD"` is half-open `[start, end)`, and `"YYYY/MM/DD"` or `"YYYY-MM"` matches the full day/month), **and** name/label the LookML measures strictly after their unfiltered calculation (`total_cost`, `total_product_retail_price`, `count`). |

## Parity checks (`pre_gate.py`), `apply_formatting`, and LookML `test:` assertions

- **Automated parity (`pre_gate.py`):** Queries raw `result_format="json"` (no `apply_formatting=True`), aligns comparison scale to `k` decimal places whenever `input.sql` projects outer `ROUND(..., k)` (`8892021.4041` matches SQL `8892021.4` at `k=2`, while enforcing 4-decimal precision on unrounded columns), accepts unscaled `percent_*` Looker values (`0.8116` / `1.1001`) against `* 100` / `100.0 *` SQL projections (`81.16` / `110.01`), canonicalizes row order inside tied rounded `ORDER BY` buckets when `ASC`/`DESC` sort keys match, and sorts normalized rows deterministically whenever `input.sql` has no top-level `ORDER BY`. Never add SQL `ROUND(...)`, `* 100` scaling, or hidden sort-helper measures in LookML just to pass `pre_gate.py`.
- **Formatted API queries (`apply_formatting=true`):** Available on `run_inline_query` / `run_query` when an interactive caller needs rendered `value_format` strings (`"$8,892,021.40"`), but never used in `pre_gate.py` or LookML tests.
- **LookML data tests (`tests/`):** Follow the terminal- vs. open-state immutability and rounding rules in [SKILL.md](../SKILL.md#state-machine-immutability--rounding-in-assertions) (`round(${view.measure}, 2|3|4) = ...` on bounded terminal historical slices; structural/algebraic invariants only on mutable open states).
