# Evaluating measures, SQL functions, and filter semantics

When translating SQL `SELECT` projections and `WHERE` clauses into LookML measures, agents must separate presentation formatting and query-time slicing from semantic aggregation. Naive 1:1 SQL translation introduces silent metric bugs (unfiltered measures with filtered names, row-level rounding drift, broken symmetric aggregates, and duplicate hidden helper measures).

Apply this guide to **every** query—including `simple_single_table` queries without `CASE WHEN`.

## SQL function and wrapper evaluation matrix

| SQL projection pattern | What it means in SQL | LookML resolution | Anti-pattern to avoid |
| :--- | :--- | :--- | :--- |
| `ROUND(<agg>, k)`, `TRUNC(<agg>, k)`, `CAST(<agg> AS NUMERIC)` | Presentation formatting (99% of queries) | Strip the outer wrapper. Model **one** native aggregate measure (`type: sum`, `type: average`, `type: number`) and set `value_format_name` (`usd`, `usd_0`, `decimal_2`) or `value_format`. | Putting `ROUND(${col}, 2)` inside `type: sum` (compiles to row-level `SUM(ROUND(col, 2))` and drifts across large tables), or splitting into a hidden `type: sum` + visible `type: number` `ROUND(${base}, 2)` pair ($2\times$ measure bloat and precision loss in downstream ratios). |
| `100.0 * <num_agg> / <den_agg>` (with or without `ROUND`) | Percentage display scaling | Strip `100.0 *` and `ROUND`. Model an unscaled `type: number` ratio (`1.0 * ${num} / NULLIF(${den}, 0)`) with `value_format_name: percent_2` (or `percent_1`, `percent_0`), or keep as a Table Calculation if one-off. | Baking `100.0 *` into LookML `sql:` alongside `percent_*` (renders `4,250%` instead of `42.5%` and breaks downstream math). |
| `COALESCE(<agg>, 0)`, `IFNULL(<agg>, 0)` | Display-layer null zeroing | Strip the wrapper. Use a native aggregate (`type: sum`, `type: count`, `type: average`). | Wrapping `COALESCE(SUM(${col}), 0)` in `type: number`, which bypasses Looker's symmetric aggregates on `one_to_many` joins. |
| `COUNT(*)` or `COUNT(pk)` (non-null PK) | Row count at table grain | Reuse the autogenerated `measure: count { type: count }`; refine its `label:` or `description:` in `bronze/:table.refinement.lkml` with an honest table-grain name. | Creating a duplicate `type: count` measure on the same view (`lkr parse lookml-to-api --validate` rejects duplicate logic). |
| `COUNT(nullable_col)` (non-PK column) | Count of rows where `nullable_col IS NOT NULL` | If `nullable_col` is a date/timestamp (`sold_at`), define a positive `type: yesno` dimension (`is_sold`: `${sold_raw} IS NOT NULL`) and filter on `filters: [is_sold: "yes"]`; otherwise `type: count` with `filters: [nullable_col: "-NULL"]` or a Custom Measure. | Mapping `COUNT(sold_at)` to unfiltered `measure: count`, which counts `NULL` rows that SQL ignored. |
| `COUNT(DISTINCT col)` | Distinct entity count | Model `type: count_distinct` with `sql: ${col} ;;` (or `APPROX_COUNT_DISTINCT` per [13-large-tables-and-partitioning.md](13-large-tables-and-partitioning.md)). | Using `type: number` with raw `COUNT(DISTINCT ...)`. |
| `SUM(col_a - col_b)` or `SUM(col_a * col_b)` | Row-level linear arithmetic before aggregation | Single-table DAG: dimension + `type: sum` in `bronze/:table.refinement.lkml`. Multi-view DAG (`${order_items.sale_price} - ${inventory_items.cost}`): dimension + `type: sum` in `silver/:view_a_:view_b_fields.view.lkml` (bare-joined). | Putting multi-view `${other_view.col}` references inside a Bronze refinement. |
| `SUM(a) / NULLIF(SUM(b), 0)` | Post-aggregation ratio | Atomic `type: sum` measures + `type: number` (`sql: 1.0 * ${total_a} / NULLIF(${total_b}, 0) ;;`), or a Query-layer Table Calculation if ad-hoc ([02-conditional-measures-and-bucketing.md](02-conditional-measures-and-bucketing.md)). | `AVG(a / b)` (average of ratios $\neq$ ratio of sums) or raw `SUM(a) / SUM(b)` inside `type: number`. |

> **When to keep SQL `ROUND` (the 1% exception):** Keep SQL rounding only when `metrics.md` or warehouse accounting rules explicitly require pre-rounded ledger math before downstream SQL subtraction/comparison, or when `ROUND(col, k)` is deliberately applied *per row* before summing (such as per-invoice tax rounding).

## `WHERE` predicates vs. intrinsic metric `filters:` ("No Lying Measure Names")

**Hard invariant:** Every LookML measure's identifier, `label:`, and `description:` must accurately describe what that measure computes **standalone** (with zero Explore `WHERE` filters applied). Never name or label an unfiltered measure after a `WHERE`-filtered SQL alias.

When an input query applies a `WHERE` predicate (or repeats the same `CASE WHEN` across projections), inspect both `input.sql` and `metrics.md` to pick one of two honest paths:

| Scenario | Signal in `input.sql` + `metrics.md` | Prescribed LookML action |
| :--- | :--- | :--- |
| **1. Intrinsic filtered domain KPI** | `metrics.md` defines a named, recurring business metric whose meaning inherently depends on the predicate (e.g., *"Unsold Dusty Shelf Inventory Cost: wholesale cash tied up in physical stock sitting unsold on warehouse shelves"* with `WHERE sold_at IS NULL`). | Bake `filters:` directly onto `sunk_dusty_shelf_cost` (`type: sum`, `sql: ${cost} ;;`, `value_format_name: usd`). When the predicate checks date/timestamp nullability (`sold_at IS NULL` / `IS NOT NULL`), promote **one** positive-polarity `type: yesno` dimension on the `raw` timeframe (`is_sold`: `${sold_raw} IS NOT NULL`, see [02-conditional-measures-and-bucketing.md](02-conditional-measures-and-bucketing.md)) and use `filters: [is_sold: "no"]`—never create negated or opposite twins (`is_unsold`, `is_not_sold`, or unrequested `sold_inventory_cost` / `total_cost` measures). |
| **2. Ad-hoc or report-level `WHERE` slice** | `WHERE` scopes a time window, region, or cohort for the query (`WHERE created_at >= '2026-01-01'`, `WHERE country = 'US'`), or filters general table metrics that are not intrinsically tied to that predicate. | Strip `WHERE` into the Explore Quick Start `query: { filters: [...] }` and `run_inline_query` `filters` (still promoting a `type: yesno` dimension if the slice is a date `NULL`/`-NULL` check), **and** name/label the LookML measures strictly after their unfiltered calculation (`total_cost`, `total_product_retail_price`, `count`). |

### Worked example (`ROUND` + `WHERE sold_at IS NULL`)

**Input SQL:**
```sql
SELECT
  COUNT(id) AS unsold_units_on_shelf,
  ROUND(SUM(cost), 2) AS sunk_dusty_shelf_cost,
  ROUND(SUM(product_retail_price), 2) AS hypothetical_retail_value
FROM `bigquery-public-data.thelook_ecommerce.inventory_items`
WHERE sold_at IS NULL;
```

**Business logic (`metrics.md`):** *"Unsold Dusty Shelf Inventory Cost adds up the total wholesale cash currently tied up in physical stock sitting unsold on warehouse shelves, alongside what that stock would fetch at full retail price. Finance reviews this number every Friday afternoon..."*

> **Avoid:** Modeling `sunk_dusty_shelf_cost` without `filters:` (standalone queries will sum sold + unsold rows) or splitting into a hidden `total_cost` (`type: sum`) + visible `type: number` `ROUND(${total_cost}, 2)` wrapper.

**Correct LookML (`bronze/inventory_items.refinement.lkml`):**
```lookml
include: "inventory_items.view.lkml"

view: +inventory_items {
  # Date NULL/-NULL check promoted to a positive type: yesno dimension on the raw timeframe.
  dimension: is_sold {
    type: yesno
    sql: ${sold_raw} IS NOT NULL ;;
    description: "Whether the inventory unit has been sold (sold_at is populated)."
  }

  # Reuses autogenerated measure: count with an honest table-grain label (NOT "Unsold Units").
  measure: count {
    label: "Inventory Units Count"
    description: "Total physical inventory units."
  }

  # Intrinsic filtered KPI: standalone queries always return unsold stock cost; usd handles 2-decimal display.
  measure: sunk_dusty_shelf_cost {
    label: "Unsold Dusty Shelf Inventory Cost"
    description: "Total wholesale cost tied up in physical stock currently sitting unsold on warehouse shelves."
    type: sum
    sql: ${cost} ;;
    filters: [is_sold: "no"]
    value_format_name: usd
  }

  # Companion unsold KPI (or total_product_retail_price without filters: if intended as a general base metric).
  measure: unsold_retail_value {
    label: "Unsold Hypothetical Retail Value"
    description: "Full retail sticker value of physical inventory stock currently sitting unsold on shelves."
    type: sum
    sql: ${product_retail_price} ;;
    filters: [is_sold: "no"]
    value_format_name: usd
  }
}
```

And in `silver/explores/inventory_items.explore.lkml`, the Quick Start `query:` (and `inline_query` payload) applies `filters: [inventory_items.is_sold: "no"]` so `inventory_items.count` is scoped to unsold items for that report while remaining honest everywhere else.

## Parity checks (`pre_gate.py`), `apply_formatting`, and LookML `test:` assertions

- **Automated parity (`pre_gate.py`):** Queries raw `result_format="json"` (no `apply_formatting=True`) and aligns comparison scale to `k` decimal places whenever `input.sql` projects outer `ROUND(..., k)` (`8892021.4041` matches SQL `8892021.4` at `k=2`), while enforcing 4-decimal precision on unrounded columns. Never add SQL `ROUND(...)` in LookML just to pass `pre_gate.py`.
- **Formatted API queries (`apply_formatting=true`):** Available on `run_inline_query` / `run_query` when an interactive caller needs rendered `value_format` strings (`"$8,892,021.40"`), but never used in `pre_gate.py` or LookML tests.
- **LookML data tests (`tests/`):** Keep measures unrounded and round inside the test assertion expression:
  ```lookml
  assert: sunk_dusty_shelf_cost_matches {
    expression: round(${inventory_items.sunk_dusty_shelf_cost}, 2) = 3102.45 ;;
  }
  ```
