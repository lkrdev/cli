# Working with large tables and partitioning (`large_tables_and_partitioning`)

This category (`large_tables_and_partitioning`) documents partition minimum dates and clustering keys in `bronze/:table.refinement.lkml`, enforces mandatory `always_filter:` guards directly in `bronze/explores/:table.explore.lkml` (`hidden: no` while unjoined; detach `:table_base.explore.lkml` with `hidden: yes` + `silver/explores/:name.explore.lkml` `extends: [:table_base]` only when cross-table joins, `*_fields`, or NDTs exist), and isolates `aggregate_table` materializations in `gold/explores/:name.explore.lkml`. Changes use Tier 2 batch confirmation.

## Tool categorization rule (`lkr parse`)

The parser tags a query with `large_tables_and_partitioning` when `parsed_query` and `queries[].aggregate_tables` satisfy any of the following conditions:

- The query targets a partitioned or clustered table in warehouse metadata, or `queries[].aggregate_tables` reports `coverage in ("hit_candidate", "partial_overlap")`.
- `parsed_query.where` or `parsed_query.columns` references `_PARTITIONTIME` or `_PARTITIONDATE`.
- `parsed_query.where` applies a non-SARGable function wrapper around a timestamp or date filter column (`WHERE DATE(created_at) = '2026-01-01'`, `WHERE EXTRACT(YEAR FROM created_at) = 2026`, `WHERE FORMAT_TIMESTAMP('%Y-%m', created_at) = '2026-01'`).
- `parsed_query.columns` uses approximate aggregations (`APPROX_COUNT_DISTINCT`, `APPROX_QUANTILES`) indicative of high-volume tables.

## Representative SQL

```sql
SELECT
  country,
  APPROX_COUNT_DISTINCT(user_id) AS approx_unique_users,
  COUNT(1) AS total_events
FROM `project.dataset.telemetry_events`
WHERE DATE(event_timestamp) >= '2026-01-01'
GROUP BY 1
```

## Impact of naive translation

1. When BigQuery tables have `require_partition_filter = true` enabled, querying the table without an explicit partition filter immediately throws a runtime fatal error (`Cannot query over table without a filter over that table's partition columns`).
2. In databases without mandatory partition enforcement, querying a 50TB table without a default date filter scans the entire historical dataset.
3. Wrapping a partition column in `DATE(event_timestamp)` or `FORMAT_TIMESTAMP(...)` inside custom dimensions prevents the warehouse query planner from pruning partitions.

## How to handle

### Model off actual columns (no redundant pseudo-dimensions)

In modern BigQuery and cloud warehouses, partitioned tables are partitioned on an actual column in the schema (`event_timestamp`, `created_at`). That column is already generated by Looker in `bronze/:table.view.lkml` as a `dimension_group` (`type: time`). Do not create redundant pseudo-dimensions like `_PARTITIONDATE` unless the table is strictly ingestion-time partitioned without any physical timestamp column in the schema. Rewrite non-SARGable date functions into the native `dimension_group` timeframes (`event_date`, `event_month`) so Looker generates SARGable range predicates (`event_timestamp >= TIMESTAMP(...) AND event_timestamp < TIMESTAMP(...)`).

### Document partition minimum date, clustering, and opaque/free-text `suggestable: no` in refinements

In `bronze/:table.refinement.lkml`, document the minimum partition date because users cannot select `"is any value"` on an `always_filter` when querying partitioned tables. Add a header comment (`# PARTITION_COLUMN: event_timestamp (DATE) | MIN_DATE: 2023-01-01 | CLUSTERED_BY: user_id, country`) and a clear `description:` to the partition dimension group specifying the physical partition boundary (`description: "Physical partition column (required). Min date available: 2023-01-01. Do not use 'is any value'."`).

Do not use `conditionally_filter:`. Instead, document clustered keys directly in their dimension `description:` (`description: "Clustering column. Filtering alongside event_date enables BigQuery block pruning."`).

On clickstream, telemetry, and large fact tables, proactively set `suggestable: no` in `bronze/:table.refinement.lkml` on opaque identifiers/codes (`sku`, `session_id`, `tracking_number`), network/path tokens (`uri`, `url`, `ip_address`), UUIDs, user agents, free-text blobs (`notes`, `comments`), and raw JSON so opening a filter dropdown does not trigger `SELECT DISTINCT` scans for values users paste verbatim. Keep human-searchable entity labels (`name`, `brand`, `title`, `city`) `suggestable: yes`; if a massive unpartitioned fact table stores denormalized labels where `SELECT DISTINCT` is costly, route suggestions via `suggest_explore:` / `suggest_dimension:` to a dimension lookup view rather than disabling `suggestable`.

### Enforce `always_filter` in Bronze Explores whenever a table has a datetime partition

Datetime partitioning is physical storage management: enforce `always_filter:` (with a safe default window like `7 days` or `30 days`) **only** when the underlying warehouse table is physically partitioned (never add `always_filter:` to unpartitioned tables just because a query filtered on `DATE(created_at)`). Place `always_filter:` directly on `bronze/explores/:table.explore.lkml` (`hidden: no`, `view_name: :table`) while unjoined. When cross-table joins, `*_fields`, or NDTs are needed, detach into `bronze/explores/:table_base.explore.lkml` (`hidden: yes`) and extend in `silver/explores/:table.explore.lkml` (`extends: [:table_base]`, `view_name: :table`)—never create joinless pass-through Silver explores.

### Use Gold aggregate awareness (`aggregate_table`) for executive rollups

If high-level daily or monthly rollups repeatedly scan a massive table, define an `aggregate_table` inside a Gold Explore (`gold/explores/:name.explore.lkml` extending `:table` with `view_name: :table` and `tags: ["gold"]`) with `partition_keys:` on the date column.

## LookML template

```lookml
# File: bronze/telemetry_events.view.lkml (Autogenerated 1:1)
view: telemetry_events {
  sql_table_name: `project.dataset.telemetry_events` ;;

  dimension: event_id {
    type: string
    primary_key: yes
    sql: ${TABLE}.event_id ;;
  }

  dimension: user_id {
    type: string
    sql: ${TABLE}.user_id ;;
  }

  dimension: country {
    type: string
    sql: ${TABLE}.country ;;
  }

  dimension_group: event {
    type: time
    timeframes: [raw, time, date, week, month, quarter, year]
    datatype: timestamp
    sql: ${TABLE}.event_timestamp ;;
  }

  measure: count {
    type: count
  }
}
```

```lookml
# File: bronze/telemetry_events.refinement.lkml
# PARTITION_COLUMN: event_timestamp (DATE) | MIN_DATE: 2023-01-01 | CLUSTERED_BY: user_id, country
include: "telemetry_events.view.lkml"

view: +telemetry_events {
  # 1. Document partition boundary so users know why "is any value" fails
  dimension_group: event {
    description: "Physical partition column (required). Min date available: 2023-01-01. Do not use 'is any value'."
  }

  # 2. Document clustering column for user filter awareness
  dimension: user_id {
    description: "Clustering column. Filtering alongside event_date enables BigQuery block pruning."
  }

  # 3. Approximate unique count for high-volume dimensions (always use ${user_id})
  measure: approx_unique_users {
    type: number
    label: "Approximate Unique Users"
    description: "HyperLogLog approximate count distinct for high-volume analysis"
    sql: APPROX_COUNT_DISTINCT(${user_id}) ;;
  }
}
```

```lookml
# File: bronze/explores/telemetry_events.explore.lkml (unjoined: hidden: no; detach to telemetry_events_base + silver/explores/ ONLY when joins exist)
include: "/bronze/telemetry_events.view.lkml"
include: "/bronze/telemetry_events.refinement.lkml"

explore: telemetry_events {
  hidden: no
  view_name: telemetry_events

  # Mandatory partition guard: prevents warehouse require_partition_filter errors
  always_filter: {
    filters: [telemetry_events.event_date: "7 days"]
  }
}
```

```lookml
# File: gold/explores/telemetry_events_daily_summary.explore.lkml (extends Silver explore when joined, or Bronze explore when single-table)
include: "/bronze/explores/telemetry_events.explore.lkml"

explore: telemetry_events_daily_summary {
  extends: [telemetry_events]
  view_name: telemetry_events
  tags: ["gold"]

  aggregate_table: daily_country_rollup {
    query: {
      dimensions: [telemetry_events.event_date, telemetry_events.country]
      measures: [telemetry_events.count]
    }
    materialization: {
      datagroup_trigger: daily_etl_datagroup
      partition_keys: ["telemetry_events.event_date"]
    }
  }
}
```

## Architecture rules

Partitioned tables are modeled directly off their physical timestamp or date `dimension_group` in Bronze (no redundant `_PARTITIONDATE` dimension and no `conditionally_filter:`). `bronze/:table.refinement.lkml` documents the minimum partition date and clustering columns in `description:` and header comments and defines `APPROX_COUNT_DISTINCT(${field})` measures (`tags: ["non_additive"]`) when needed; `bronze/explores/:table.explore.lkml` (`hidden: no` until joined in Silver) enforces `always_filter:`.
