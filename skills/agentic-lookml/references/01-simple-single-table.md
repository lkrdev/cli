# Simple single-table queries (`simple_single_table`)

This category (`simple_single_table`) covers single-table queries that map to `bronze/:table.view.lkml` (autogenerated) and on-demand `bronze/:table.refinement.lkml` files for dimensions, primary keys, high-cardinality `suggestable: no` governance, and single-table measures. Unjoined single-table queries are served directly from `bronze/explores/:table.explore.lkml` (`explore: :table`, `hidden: no`) until a cross-table join, `silver/*_fields.view.lkml` view, or Silver NDT/SDT is needed—at which point the Bronze explore is detached into `bronze/explores/:table_base.explore.lkml` (`explore: :table_base`, `hidden: yes`) and promoted to `silver/explores/:table.explore.lkml` (`explore: :table`, `extends: [:table_base]`, `hidden: no`). Queries in this category qualify for Tier 1 auto-application.

## Tool categorization rule (`lkr parse`)

The parser tags a query with `simple_single_table` when `parsed_query` meets all of these conditions:

- `len(parsed_query.tables) == 1` (a single physical table).
- `parsed_query.joins == []` (no `JOIN` or `UNNEST` joins).
- `parsed_query.ctes == []` and no nested `FROM (SELECT ...)` subqueries.
- `parsed_query.statement_type == "SELECT"` (no `UNION`).
- Every `col` in `parsed_query.columns` has `col.sql` containing only direct columns, simple scalar functions (`DATE_TRUNC`, `COALESCE`), or standard single-pass aggregations (`col.is_agg == True` with `COUNT`, `COUNT(DISTINCT ...)`, `SUM`, `AVG`, `MIN`, `MAX`, and no nested `CASE` or window functions).

## Representative SQL

```sql
SELECT
  status,
  DATE_TRUNC(created_at, MONTH) AS created_month,
  COUNT(*) AS row_count,
  SUM(sale_price) AS total_revenue
FROM `project.dataset.orders`
WHERE created_at >= '2026-01-01'
GROUP BY 1, 2
```

## Impact of naive translation

1. Modifying `bronze/orders.view.lkml` directly gets overwritten on the next schema sync because base Bronze views are autogenerated.
2. Putting cross-view dimensions or measures in Bronze (or inside a single table's view refinement) breaks layer boundaries and view portability. Bronze can hold dimensions and measures only when their entire dependency DAG references that single table; any dimension or measure that anywhere in its DAG references multiple views belongs in its own `silver/:view_a_:view_b_fields.view.lkml` view and is bare-joined into the Explore.
3. Creating `bronze/:table.refinement.lkml` when no non-generator transformations, single-table measures, primary keys, or descriptions are being added clutters `bronze/` with empty refinement files.
4. Creating empty pass-through Silver Explores (`silver/explores/:table.explore.lkml`) when a single-table query has zero cross-table joins, or routing standalone `FROM :entity` queries (`FROM users`) onto a fact `LEFT JOIN` explore (`FROM order_items LEFT JOIN users`, which drops 0-order users).

## How to handle

### Bronze base view (`bronze/:table.view.lkml`)

Inspect `queries[].parsed_query.tables` and `queries[].views` in `lkr parse sql-lookml-compare`. Compare each physical table in `parsed_query.tables` against `views`, and compare the SQL columns extracted from the query against `views[].fields` and `views[].unmodeled_db_columns`.

Looker's generator automatically outputs 1:1 physical dimensions, `dimension_group` blocks for timestamps and dates, and the default `measure: count { type: count }`. If `bronze/:table.view.lkml` does not exist yet in `views` or if physical columns are missing in `views[].unmodeled_db_columns`, follow the [generate-view-from-table](../../generate-view-from-table/SKILL.md) skill (`lkr tools lookml create --folder bronze`, `generate_lookml_with_new_files`, or MCP `generate_view_from_table` / `create_view_from_table`) to autogenerate or refresh `bronze/:table.view.lkml`, pull it locally, and re-run `lkr parse sql-lookml-compare`. Never hand-edit `bronze/:table.view.lkml`.

### Bronze refinement (`bronze/:table.refinement.lkml`, on-demand only)

Do not create `bronze/:table.refinement.lkml` automatically. Only create it when adding transformations, single-table measures (`sum`, `average`, `count_distinct`, single-table filtered measures, and single-table ratios), single or composite primary keys, `suggestable: no` on high-cardinality string or raw JSON columns (`session_id`, `uri`, `ip_address`, UUIDs, URLs, JSON), `hidden: yes` flags, partition metadata comments, or descriptions and labels that the generator does not produce. Every dimension and measure in a Bronze refinement must only reference fields within that single table across its entire dependency DAG.

Evaluate every projected SQL aggregate and `WHERE` predicate using [measures-and-sql-functions.md](measures-and-sql-functions.md): normalize colloquial SQL `AS` aliases (`unique_chaotic_sessions`, `distinct_clicking_humans`) into canonical LookML identifiers (`unique_sessions` / `session_count`, `distinct_users` / `user_count`—avoiding `*(id|year|decade)` suffixes on counts), strip cosmetic outer `ROUND(<agg>, k)` / `COALESCE(<agg>, 0)` wrappers in favor of a single native measure (`type: sum`, `type: average`) with `value_format_name` (`usd`, `decimal_2`), reuse `measure: count` for `COUNT(*)` / `COUNT(pk)` (using `filters: [col: "-NULL"]` for `COUNT(nullable_col)`), and never name or label an unfiltered measure after a `WHERE`-filtered SQL alias.

### Bronze-until-join Explores and Silver promotion

Any dimension or measure that anywhere in its dependency DAG references different views belongs in its own dedicated Silver view named by sorting the referenced view names alphabetically and appending `_fields` (`silver/:view_a_:view_b_fields.view.lkml`), and is bare-joined (`sql: ;;`, `relationship: one_to_one`) into the Explore that joins those views together. For example, if `order_items.gross_margin` is `${order_items.sale_price} - ${inventory_items.cost}` and `order_items.total_gross_margin` is `SUM(${order_items.gross_margin})`, move both `gross_margin` and `total_gross_margin` (`type: sum`, `sql: ${gross_margin} ;;`) into `silver/inventory_items_order_items_fields.view.lkml` and bare-join `inventory_items_order_items_fields` into the Explore that joins `order_items` and `inventory_items`.

Before creating or promoting an Explore, inspect `queries[].explores` and `queries[].explore_queries`:
- **Existing Silver Explore anchored on `:table`:** If `silver/explores/:table.explore.lkml` already exists with `view_name: :table`, serve the query and add Quick Start `query:` blocks there (keeping `bronze/explores/:table_base.explore.lkml` `hidden: yes`). Never route a standalone `FROM :entity` query (`FROM users`) onto a fact `LEFT JOIN` explore (`FROM order_items LEFT JOIN users`), which excludes entities with zero activity.
- **Unjoined single-table query (no Silver explore yet):** Serve single-table queries (fact or entity tables such as `events`, `inventory_items`, `users`, `products`, `distribution_centers`, excluding utility spines like `calendar_dates` or `common_helpers`) directly from `bronze/explores/:table.explore.lkml` (`explore: :table`, `hidden: no`, `label: "..."`, `view_name: :table`, plus Quick Start `query:` blocks) and test in `tests/bronze/:table.test.lkml` (`explore_source: :table`). Do **not** create a joinless pass-through file in `silver/explores/`.
- **Detaching Bronze and promoting to Silver when a join is needed:** As soon as `:table` requires a cross-table `join:`, a `silver/*_fields.view.lkml` bare join, or a Silver NDT/SDT (for example, joining `orders` or `user_order_facts` onto `users` to analyze a user's number of orders), detach the Bronze explore into `bronze/explores/:table_base.explore.lkml` (`explore: :table_base`, `hidden: yes`, `view_name: :table`, updating `tests/bronze/:table_base.test.lkml` to `explore_source: :table_base`) and create `silver/explores/:table.explore.lkml` (`explore: :table`, `extends: [:table_base]`, `hidden: no`, `label: "..."`, `view_name: :table`, moving Quick Start `query:` blocks there and adding the required `join:`s). Keeping the public explore name `:table` preserves `/x/` URLs, Saved Looks, Dashboards, and snapshot keys without breakage. Follow strict YAGNI on joins: never speculatively join unreferenced Bronze views when the input SQL and `metrics.md` do not require them, and when an entity table only appears in a `JOIN` on a fact query (`FROM orders JOIN users`), join `users` into `silver/explores/orders.explore.lkml` without creating a standalone public `users` explore.

For `WHERE` predicates, check `metrics.md` ([measures-and-sql-functions.md](measures-and-sql-functions.md) and [02-conditional-measures-and-bucketing.md](02-conditional-measures-and-bucketing.md)): promote date/timestamp `NULL` / `NOT NULL` predicates (`sold_at IS NULL`) to a positive `type: yesno` dimension (`is_sold`: `${sold_raw} IS NOT NULL`); if `metrics.md` defines an intrinsic filtered domain KPI (*Unsold Inventory Cost*), put `filters: [is_sold: "no"]` directly on that measure (skipping unrequested unfiltered base measures); if `WHERE` is an ad-hoc query slice (`created_at >= '2026-01-01'`), map it to runtime Explore filters (`query: { filters: [...] }` Quick Start blocks or `WriteQuery.filters`) and give the measures strictly unfiltered names (`total_revenue`, `count`). Note that Looker's `explore: { query: {} }` Quick Start syntax only supports modeled `dimensions`, `measures`, `filters`, `pivots`, `subtotals`, `limit`, `sorts`, `timezone`, and `description`; Table Calculations and Custom Fields cannot be placed inside an `explore: { query: {} }` block.

## LookML template (single-table measures in Bronze refinement)

```lookml
# File: bronze/orders.refinement.lkml
# (Created because total_revenue is not generated automatically; its entire DAG references only orders)
include: "orders.view.lkml"

view: +orders {
  measure: total_revenue {
    type: sum
    sql: ${sale_price} ;;
    value_format_name: usd
    description: "Sum of order sale price."
  }
}
```

## Architecture rules

The `bronze/:table.view.lkml` file is strictly autogenerated (`1:1` physical columns plus `measure: count`) and never hand-edited. The `bronze/:table.refinement.lkml` file is created on-demand only when adding primary keys, single-table measures, custom dimensions or durations, `suggestable: no` high-cardinality governance, partition metadata comments, or descriptions whose entire dependency DAG stays within that single table.

Single-table unjoined queries use `bronze/explores/:table.explore.lkml` (`explore: :table`, `hidden: no`) directly without creating empty `silver/explores/` wrappers; when a cross-table join, `silver/*_fields.view.lkml` view, or Silver NDT/SDT is needed, detach Bronze into `bronze/explores/:table_base.explore.lkml` (`explore: :table_base`, `hidden: yes`) and create `silver/explores/:table.explore.lkml` (`explore: :table`, `extends: [:table_base]`, `hidden: no`). Any dimension or measure whose dependency DAG spans multiple views lives in `silver/:view_a_:view_b_fields.view.lkml` and is bare-joined (`sql: ;;`) into the Silver Explore.
