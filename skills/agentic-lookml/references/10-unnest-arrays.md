# Working with `UNNEST` and array data (`unnest_arrays`)

This category (`unnest_arrays`) models inline scalar array subqueries in `bronze/:table.refinement.lkml` (Tier 1 auto-application) and `1:M` repeated array expansions in `bronze/:table__:array.view.lkml` paired with `bronze/explores/:table_base.explore.lkml` (`extension: required`) and `silver/explores/:table.explore.lkml` (`extends: [table_base]`) (Tier 2 batch confirmation).

## Looker autogeneration behavior for `STRUCT` and `REPEATED`

Before writing LookML for nested fields, check what Looker's project generator already created in `bronze/`:

1. For scalar `STRUCT` columns (`RECORD` mode `NULLABLE`), Looker does not create a separate view. Instead, it generates dot-notation dimensions directly inside `bronze/:table.view.lkml`:
   ```lookml
   dimension: geo__city {
     type: string
     sql: ${TABLE}.geo.city ;;
     group_label: "Geo"
   }
   ```
2. For `REPEATED` records (`ARRAY<STRUCT>` or `ARRAY<SCALAR>`), Looker autogenerates a companion view in `bronze/` using a double underscore: `bronze/:table__:repeated_col.view.lkml` (for example, `events__event_params.view.lkml` or `orders__line_items.view.lkml`). This autogenerated view has no `sql_table_name`, contains dimensions for each element field (`${TABLE}.key`, `${TABLE}.value.string_value`), and includes an autogenerated `measure: count { type: count }`.
3. When generating views for tables with repeated fields, place the `UNNEST` join in a non-user-facing Bronze base explore (`bronze/explores/:table_base.explore.lkml` with `extension: required`):
   ```lookml
   explore: events_base {
     extension: required
     view_name: events

     join: events__event_params {
       view_label: "Events: Event Params"
       sql: LEFT JOIN UNNEST(${events.event_params}) AS events__event_params ;;
       relationship: one_to_many
     }
   }
   ```
   Intra-table `UNNEST` joins are one of the four physical table exceptions where an explore in `bronze/explores/` is permitted (`extension: required` or `hidden: yes`), because the `UNNEST` join reflects the internal physical structure of a single database table rather than a semantic join across separate physical entities. The `silver/explores/:table.explore.lkml` file then extends `events_base` (`extends: [events_base]`, `view_name: events`).

## Tool categorization rule (`lkr parse`)

The parser tags a query with `unnest_arrays` when the AST (`columns[].sql`, `where`, or `joins`) contains either pattern:

- `UNNEST` or `EXPLODE` in `FROM` or `JOIN` (`CROSS JOIN UNNEST(t.items)`, `LEFT JOIN UNNEST(t.tags) AS tag`, `FROM table, UNNEST(items)`).
- An inline correlated `UNNEST` subquery inside `SELECT` or `WHERE` (`(SELECT value.string_value FROM UNNEST(event_params) WHERE key = 'page_location')`).

## Representative SQL

```sql
-- Archetype 10A: Inline Scalar Array Extraction (1:1 per parent row, e.g., GA4 event_params)
SELECT
  event_id,
  (
    SELECT value.string_value
    FROM UNNEST(event_params)
    WHERE key = 'page_location'
    LIMIT 1
  ) AS page_location
FROM `project.dataset.events`;

-- Archetype 10B: 1:M Repeated Struct Expansion (Order Line Items / Tags)
SELECT
  o.country,
  item.category AS item_category,
  COUNT(DISTINCT o.order_id) AS order_count,
  SUM(o.shipping_fee) AS total_shipping_fee,
  SUM(item.price * item.quantity) AS item_revenue
FROM `project.dataset.orders` AS o
LEFT JOIN UNNEST(o.line_items) AS item
GROUP BY 1, 2;
```

## Impact of naive translation

1. Joining `UNNEST(o.line_items)` multiplies parent `orders` rows by $N$ items. Without `primary_key: yes` on `orders` and `relationship: one_to_many` on the `UNNEST` join, `SUM(o.shipping_fee)` is inflated $N\times$.
2. Using `CROSS JOIN UNNEST` (or `, UNNEST(...)`) in the Explore drops parent rows with empty or `NULL` arrays even when the user has not selected any array fields.

## How to handle

| `UNNEST` pattern | Grain impact | Resolution | Target layer |
| :--- | :--- | :--- | :--- |
| Key-value lookup inside array (`WHERE key = 'x' LIMIT 1`) | `1:1` (preserves parent row grain) | Extract as a scalar dimension in `bronze/:table.refinement.lkml` using an inline `(SELECT ... FROM UNNEST(${arr}) WHERE ... LIMIT 1)` expression referencing the LookML dimension `${arr}` (never `${TABLE}.arr`). No join needed. | `bronze/:table.refinement.lkml` |
| Single-row array aggregation (`ARRAY_LENGTH`, `(SELECT SUM(x.amt) FROM UNNEST(${arr}) x)`) | `1:1` (preserves parent row grain) | Define as a dimension or `type: sum` measure wrapping the inline `UNNEST(${arr})` subquery in `bronze/:table.refinement.lkml`. No fanout. | `bronze/:table.refinement.lkml` |
| `1:M` repeated `ARRAY<STRUCT>` or `ARRAY<SCALAR>` used for grouping or filtering | `1:M` (expands 1 parent row into $N$ child rows) | Define a virtual `UNNEST` view (`bronze/:table__:array_col.view.lkml`, no `sql_table_name`) with a `WITH OFFSET` composite PK, declare the `sql: LEFT JOIN UNNEST(${parent.array_col}) AS child WITH OFFSET AS child_offset ;;` (`relationship: one_to_many`, never `sql_on:`) in `bronze/explores/:table_base.explore.lkml` (`extension: required`), and extend it in `silver/explores/:table.explore.lkml`. | `bronze/:table__:array.view.lkml` + `bronze/explores/:table_base.explore.lkml` + `silver/explores/:table.explore.lkml` |

## LookML templates

### Inline `1:1` key-value extraction (`bronze/events.refinement.lkml`)

```lookml
# File: bronze/events.refinement.lkml
include: "events.view.lkml"

view: +events {
  dimension: page_location {
    type: string
    # Always reference the actual parent dimension ${event_params}, NEVER ${TABLE}.event_params
    sql: (
      SELECT value.string_value
      FROM UNNEST(${event_params})
      WHERE key = 'page_location'
      LIMIT 1
    ) ;;
  }
}
```

### Virtual `1:M` `LEFT JOIN UNNEST` view (`bronze/` and `silver/explores/`)

```lookml
# File: bronze/orders__line_items.view.lkml
view: orders__line_items {
  dimension: pk {
    primary_key: yes
    hidden: yes
    type: string
    sql: CONCAT(CAST(${orders.order_id} AS STRING), '_', CAST(orders__line_items_offset AS STRING)) ;;
  }

  dimension: category {
    type: string
    sql: ${TABLE}.category ;;
  }

  dimension: line_total {
    type: number
    sql: ${TABLE}.price * ${TABLE}.quantity ;;
  }

  measure: item_revenue {
    type: sum
    sql: ${line_total} ;;
    value_format_name: usd
  }
}
```

```lookml
# File: bronze/explores/orders_base.explore.lkml
include: "/bronze/orders.view.lkml"
include: "/bronze/orders.refinement.lkml"
include: "/bronze/orders__line_items.view.lkml"

explore: orders_base {
  extension: required
  view_name: orders

  join: orders__line_items {
    view_label: "Order Line Items"
    sql: LEFT JOIN UNNEST(${orders.line_items}) AS orders__line_items WITH OFFSET AS orders__line_items_offset ;;
    relationship: one_to_many
  }
}
```

```lookml
# File: silver/explores/orders.explore.lkml
include: "/bronze/explores/orders_base.explore.lkml"

explore: orders {
  extends: [orders_base]
  view_name: orders
}
```

## Architecture rules

Virtual `UNNEST` companion views always live in `bronze/:table__:array_col.view.lkml` (matching Looker's double-underscore naming convention) and are joined using `sql: LEFT JOIN UNNEST(${parent.array_col}) ... ;;` (never `sql_on:`) inside `bronze/explores/:table_base.explore.lkml` (`extension: required`), which is then extended by `silver/explores/:table.explore.lkml`.

Every `1:M` unnested array view that lacks a guaranteed unique element ID must use `WITH OFFSET AS <alias>_offset` in the `LEFT JOIN UNNEST` clause and define `CONCAT(CAST(${parent.pk} AS STRING), '_', CAST(<alias>_offset AS STRING))` as its `primary_key: yes`. Inline `1:1` scalar `UNNEST` subqueries must always reference the LookML dimension `UNNEST(${array_dim})` and never reference `${TABLE}.array_col` inside `UNNEST`.
